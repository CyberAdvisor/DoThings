## What this is
A local web front end to Things 3. `serve.py` (Python standard library, 3.9) serves `index.html` at `http://127.0.0.1:8765`. It reads the Things SQLite database read-only and changes tasks through `things:///update` URLs using the user's auth token. The Today list is shown in five priority groups based on the tags P1 (Due Today), P2 (To Do), P3 (Follow Up), P4 (Next Up, v1.1.0) and P5 (unnamed, v1.6.0). The names are the user's (Settings, v1.6.0); the tags are fixed.

## Rules (the core of the app)
On every list refresh (page load, window focus, every 60 seconds), each Today task is checked in this order:
1. Overdue or due today → P1.
2. Several P tags → keep the highest.
3. No P tag → in a sequential project, the priority set for its tag in Settings (`sequence_priority(task.project_tags, settings)`, v1.7.0; v1.2.0–v1.6.0 used P4 for Next Up projects); otherwise the default priority from Settings (P2 unless changed, v1.6.0).
4. No start date (Inbox, Anytime or Someday) and due today or overdue → start date set to today (`when=YYYY-MM-DD`), so it is in Things' own Today too. Combined with any retag into one change.

Refresh changes never touch deadlines.

Editor: choosing Someday or Anytime for When also clears the deadline (`plan_edit`), unless the same edit sets one. Deferring the start to a date after today moves a deadline that is before that date to it (so the task leaves Today), unless the same edit sets or clears the deadline; The page doesn't apply these rules: each date or priority choice asks `POST /api/edit/preview`, which runs `plan_edit` and `predict` (the change, then the refresh rules if the task is in Today) and returns the resulting When, deadline and priority, the row (`task_to_json`) and its place in the list being shown (`view_check.place_in_view` for the group key in Today's view and tag, `search_check.matches` for "list" in a search, or null). Save fetches a final preview and puts that row in place before the write is confirmed (v0.1.27). A deadline chosen in the card is sent with a When change even if unchanged, so the defer rule doesn't move it.

Manual moves:
- All P tags are replaced with the destination tag.
- A deadline after today is kept on every move (v0.1.25).
- Into P1 → a missing deadline is set to today.
- Out of P1 → a deadline of today or earlier is cleared (an overdue one must go, or the refresh rules put the task straight back in P1). If the task is in Today only because of its deadline (no start date, or one after today), its start date is also set to today (`when=YYYY-MM-DD`), so it stays in Today.
- Among P2 to P5 → the deadline is unchanged.
- With Settings' auto_p1 off (v1.6.0) rule 1 doesn't run (a due task keeps its priority; untagged gets the default) and no move changes the deadline. Rule 4 (start date for a due undated task) still runs, so due tasks stay in Today. The editor's "so it will be P1" note disappears by itself, since the preview's priority then matches the choice.

The "source" priority of a move is `required_priority` (what the rules say), not just the current tag. So an overdue task still tagged P2 counts as P1, and moving it to P2 clears its deadline.

Without the start-date step, clearing the deadline of a deadline-only task would drop it out of Today. Keep `set_start_date` in `plan_move`.

## Data model
- `Task`: uuid, title, tags, start_date, deadline, context (project or area title), project_tags (its project's tags, directly or via its heading; v1.7.0).
- `Change`: task_id, the full `tags` list, `set_deadline` or `clear_deadline`, and optionally `set_start_date`. `is_satisfied_by(task)` is how a write is confirmed.
- `Settings.sequence_tags` (v1.7.0): (project tag, priority) pairs from Settings › Sequential projects, empty for new users. `parse_settings` refuses an empty or multi-line tag, a P tag, a tag listed twice and a priority outside P1–P5; tags are trimmed and matched exactly. Do Things never changes projects (`ProjectChange` and the `update-project` write were removed in v1.7.0).
- `task_order.json`: `{"P1": [ids], ..., "P5": [ids], "all": [ids], "project:<id>": [ids], "project:none": [ids]}` (the last three since v2.0.0, one per Today view group). Every list request drops ids no longer in Today (`prune_order`, which also drops empty view lists) and saves only if something was dropped. Ids not listed appear after the listed ones, in Things' `todayIndex` order (All: by priority, then the Priority view's order). `update_order` removes moved ids from the other groups of the same view only, so an id is never listed twice in one view and a priority move leaves the All and Project orders alone.

## Things database facts
- Reading it needs macOS permission for the app that starts Do Things: System Settings › Privacy & Security › Files & Folders › (Terminal or Shortcuts) › "Data shared by Things and affiliated apps". macOS asks the first time ("would like to access data from other apps"). Without it, access is blocked and the database is reported as not found. Full Disk Access is not needed (corrected in v1.0.2).
- Location: `~/Library/Group Containers/JLMPQHK86H.com.culturedcode.ThingsMac/ThingsData-*/Things Database.thingsdatabase/main.sqlite`. Older versions have no `ThingsData-*` folder. Both layouts are searched, and the newest file wins.
- `TMTask`:
  - `type` 0 = to-do.
  - `status` 0 open, 2 canceled, 3 completed.
  - `start` 0 Inbox, 1 Anytime, 2 Someday.
  - `trashed`.
  - A to-do keeps `status` 0 and `trashed` 0 when its project or heading is trashed, completed or canceled, so queries also check the project (`project`), heading (`heading`) and heading's project. Trashed parents hide to-dos from every list; closed parents hide them from open lists.
  - `startDate` and `deadline` are packed ints (`year<<16 | month<<12 | day<<7`).
  - `reminderTime` is a packed int (`hour<<26 | minute<<20`), NULL with no reminder; checked against real 9:15 AM and 3:00 PM reminders on 2026-11-08 (v1.3.1, `debug_things.py` prints raw and decoded values). Decoded by `unpack_things_time`; an invalid value means no reminder.
  - `todayIndex` gives the Today order.
  - `rt1_recurrenceRule` is non-null on repeating templates, which are excluded.
- Project order: `TMTask."index"` is a to-do's manual position in its project or heading; headings have their own `index` in the project, and unheaded to-dos come first (`Task.project_rank`). `in_project_order` fills each project's Today slots in project order; the saved Do Things order (`task_order.json`) still wins.
- Sequential projects (v1.7.0): an open project with a tag listed in Settings (`settings.sequence_tag_names`); before v1.7.0 the tags `Sequential` and `Next Up` were built in. `read_sequential_projects(conn, tags)` reads each one's open to-dos across the whole project (none listed: no projects). The task in progress (`sequence_next`) is the first, in project order, with no deadline, not Someday, and no start date or one of today or earlier. If it has no start date, `plan_sequence` sets it to today; the refresh does this before the Today rules, so the task also gets its tag's priority in the same refresh. Nothing is hidden (v0.1.15 hid tasks; replaced in v0.1.16).
- Tag priorities (v1.7.0, replacing Next Up's fixed P4 from v1.1.0): rule 3 gives an untagged Today to-do of a sequential project its tag's priority, whoever dated it. A project with two listed tags uses the higher priority (`sequence_priority`); the other tag is ignored, never removed (v1.1.0–v1.6.0 removed `Next Up` from a project also tagged `Sequential` with `things:///update-project`). A changed priority only affects tasks tagged from then on (rule 3 skips tagged tasks). Michael's own setup: `Sequential` → P2 and `Next Up` → P4 (Next Up's purpose, in his words: lower-priority projects that don't need immediate action but that you want to be reminded of, such as books to read, shows to watch or chores to do).
- Missing sequential-project tags (v1.7.0): `missing_tags(conn, settings.sequence_tag_names)` is sent as `missing_sequence_tags` in the list and settings responses. Settings shows "Not found in Things" on the row, and Today an amber, non-blocking notice with a link to Settings › Sequential projects (`showSettings("sequence-settings")`). It blocks nothing: no project can carry a tag that doesn't exist.
- Reset other tasks (v1.2.0): the editor of a task in a sequential project (`task_detail` sends `sequence_project` when `sequence_priority` finds a listed tag) offers "Reset other tasks". `plan_sequence_reset(project_tasks, keep, today)` sends every other open to-do of the project with a start date of today or earlier and no deadline back to Anytime without P tags (the same change as the undo, `_back_to_anytime`); tasks with a deadline, later starts, Someday and completed ones are untouched. If the kept task has no start date (due only) it gets `when=today` first. `serve.reset_sequence` records the kept task as a `Pull` with no `after`, so the next refresh treats it as in progress and doesn't start the first undated task again; the record is saved only after the kept task's own change is confirmed. The page shows the server's preview (`/api/sequence/reset/preview`) with a reminder to check the project order in Things (returned tasks keep their position; the URL scheme can't move them; the user chose not to use the complete-and-reopen trick that moves a task to the bottom).
- Records of unlisted projects (v1.7.0): `step_sequences` keeps `sequence_pulls.json` records of projects it doesn't step (tag removed from Settings, or no open to-dos) but never acts on them, so a tag added back picks its task in progress up again (marker and undo); a stepped project's record is dropped when it no longer matches, as before. Chosen so the gap between updating to v1.7.0 and re-adding the tags loses nothing.
- Settings page (v1.7.0): `settingsStore` holds the saved settings for both sections, so a save in one never sends the other's stale values. `sequenceSettings` redraws rows only when one is added or removed (focus isn't lost while typing); a row is saved once its tag is typed, and only the first row with a given tag shows a status.
- Undo (v0.1.17, reworked v0.1.18): `serve.step_sequences` records each started task as a `Pull` (task, date given, `after` = the project's most recently completed task, `read_last_completed`) in `sequence_pulls.json`. Things moves a completed-then-reopened task to the bottom of the project (its `index` changes), so project order can't detect an unchecked task. While a recorded task is open with its date it is in progress and nothing else is started. When its `after` task is open again, `plan_sequence_undo` sends it back to Anytime and the reopened task is recorded as in progress (with no `after`, so it is never undone). Records from v0.1.17 have no `after` and are never undone. The undo sends `when=anytime` and removes the task's P tags (`tags=` with the remaining tags, possibly empty). `find_pulled` drops the record if the task was completed or its start date no longer matches (the user changed it), so user-dated tasks are never undone. Tests patch the record path into their temporary folder.
- Rows mirror Things (v0.1.19): `task_to_json` sends the tags without P tags; in searches that can list more than one priority (`shows_priority_pills`: any search not limited to exactly one; v1.9.0, before only Overdue) it also sends `priority` (the task's P tag), which the page shows as a colored pill with the priority's name from `priority_names` (v1.6.0; before, the P tags were sent among the tags), `deadline_label` ("N days ago" / "today" / "N days left"), `start_label` (weekday within a week, else "Nov 14"; only for later starts), `has_notes`, `has_checklist`, `repeating` (`rt1_repeatingTemplate` set), `reminder_label` ("2:30 PM", shown in gray after the title; v1.4.0). The editor's When (`when_json`) carries the same label, shown read-only after the date. Reminders are display only: no rule uses them, and Do Things never sets them. The edit preview leaves the reminder out when When changes, and the reloaded row shows what Things kept. Tested 2026-11-08 with a real task: after a URL-scheme `when` change Things keeps the reminder for a date (incl. Tomorrow) or Anytime and removes it for Someday. Predicting that in the preview was offered; the user preferred the current behavior. The editor's tag list is `other_tags` (no P tags; priority is separate). Tag order is the database's, not Things' tag order.
- Checklists: `TMChecklistItem(task, status)`; status other than 0 (completed or canceled) counts as done. Shown read-only as progress in the editor.
- "Hide Completed" (sidebar checkbox, saved in the browser's localStorage as `dothings.hideCompleted`) adds `hide_completed=1` to `/api/list`, which drops today's completed tasks from the list but not from the counts.
- "Hide Empty" (v1.3.0, sidebar checkbox, `dothings.hideEmpty`) is page-only: `renderGroup` marks a Today group with no tasks (after Hide Completed) `unfilled`, and CSS hides those while `body.hide-empty` is set, except while a task is dragged (`body.dragging-task`, added in a `setTimeout` because changing the layout inside `dragstart` cancels the drag in Chrome), so every priority stays a drop target. `fillZone` unhides a group when a drop or an editor save puts a task in it. A "Nothing here." line shows only when Hide Empty hides every group. Applies to Today's groups only (user's choice), not the sidebar searches.
- Sidebar counts come with every list response: Inbox = open, untrashed to-dos with `start` 0; Today: red badge = open tasks due today or overdue, gray number = the other open Today tasks (`today_counts`: `due`, `not_due`), as in Things.
- Tags: `TMTaskTag(tasks, tags)` joins `TMTag(uuid, title)`. Tag titles are concatenated with `char(31)` because titles can contain commas.
- Today = open to-dos with `start` in (1, 2) and `startDate <= today`, plus tasks with `deadline <= today` (excluding those with `deadlineSuppressionDate` set, when that column exists).
- Every list shows open to-dos plus those completed since local midnight (`status` 3 and `stopDate` ≥ midnight; `stopDate` is Unix time). They come back as `Task.completed_at`, are sorted after open tasks (`completed_last`, oldest completion first), are skipped by the refresh rules, and can't be moved. Canceled to-dos are never shown.
- Task reads also return `notes`, Someday state (`start` 2 with no `startDate`), `list_id` (`COALESCE(t.project, heading's project, t.area)`) and `heading_id`. A to-do under a heading has `heading` set and `project` NULL.
- Searches (v1.9.0) read Today (`_TODAY_CLAUSE`) or every open to-do (`read_list(conn, "open", …)`) and filter in Python (below).
- Do Things only queries Today and every open to-do (`OPEN_LISTS`, for the searches). Inbox, Upcoming, Anytime, Someday and Logbook open in Things with `things:///show?id=<list>` (no token needed).

## Saved searches (v1.9.0)
- Decided with Michael 2026-11-10 (mockups row 4, approved as drawn): the fixed P1–P4 and Overdue searches became user-built searches. Criteria: priority, tag, text (title or notes, ignoring case), project or area, deadline (Any or Overdue = before today). Criteria combine with AND; within priority, tags and projects any chosen value matches (Michael's choice of several values per field). Each search has a scope: Today (default) or all open tasks (Michael's choice to keep Overdue's old reach as an option for any search).
- Gotcha found while testing: Do Things' Today already includes every task due today or overdue, whatever its start date, so the default Overdue search lists the same tasks with either scope. The scope matters for other criteria (e.g. a tag across Someday and Anytime tasks).
- `search_check.Search` (id, name, scope, priorities, tags, text, lists, overdue). `searches.json` (`{"searches": [...]}`, untracked) holds them in sidebar order; missing or invalid → `DEFAULT_SEARCHES` (ids `p1`–`p4`, `overdue`: the old list names, so a page or test using them keeps working). An empty list is kept (the user deleted them all). Names are unique ignoring case; at most 50 searches, 20 tags or projects each; P tags are refused as tags (Priority covers them). New ids are `s1`, `s2`, … (`new_search_id`).
- Separate file, not `settings.json` (Michael had no preference): the Settings page posts its whole settings object, so a shared file would let one save overwrite the other.
- Matching uses the task's current P tag (`current_priority`); a task outside Today has usually no P tag, so a priority search finds it only if it was tagged. Projects and areas match `Task.list_id` (the project, directly or via its heading, else the area); choosing an area doesn't include its projects' tasks. A tag or project no longer in Things matches nothing; the builder marks it "Not found in Things" and `describe` says "a project or area not in Things".
- Order: soonest deadline first, none last; ties keep the input order (Today's project order, or Things' `index` for all open tasks).
- API: `GET /api/list?name=<today|search id>` (unknown → 404; the page then goes back to Today); every list response has `searches` (id, name) for the sidebar, a search's also `search` and `summary`. `POST /api/searches/preview` (read only, no refresh rules; empty name allowed while choosing) returns rows, summary and `choices` (tags, areas and projects). `POST /api/searches/save` (empty id = new) and `/api/searches/delete` (after the page's confirmation) change only `searches.json`.
- Page: `openBuilder(search|null)` sets `state.view = "builder"` (so `load()` doesn't redraw over it) with a draft; each choice calls `changeDraft` (redraw the form, then `refreshBuilder`), text fields update the draft and refresh after a 300 ms pause; only the latest preview answer is drawn (`seq`). Builder rows are `inert` (no click, check or drag). The Searches heading toggles `state.searchesCollapsed` (localStorage `dothings.searchesCollapsed`); + opens a new search. Switching lists, Settings or Cancel discards the draft.

## Calendar events (v1.8.0)
- Things doesn't store events in its database; it reads macOS Calendar live. Do Things reads them through EventKit from JavaScript for Automation (`osascript -l JavaScript`, script on stdin), standard library only. Confirmed on Michael's Mac (macOS 27.2, 2026-11-10) with `debug_calendar.py` v1.7.1: macOS showed the calendar prompt for Terminal, full access was granted, a read took about 20 ms, and a test event came back with the right time and calendar. The AppleScript route (Calendar app) was dropped: its `whose` date query failed (-1726), and it is slow and misses repeating events.
- EKAuthorizationStatus: 0 not determined, 1 restricted, 2 denied, 3 full access (authorized before macOS 14), 4 write only; `calendar_check.ACCESS_BY_STATUS` names them (not_asked, restricted, denied, allowed, write_only), plus `unavailable` when osascript fails.
- Gotcha: the access request's completion block never arrived in osascript (the v1.7.1 diagnostic waited its full 80 s although access was granted). `CALENDAR_REQUEST_SCRIPT` therefore polls the access status instead (up to 60 s).
- Two scripts share `_CALENDAR_JS`: `CALENDAR_READ_SCRIPT` (never asks; every refresh and Settings) and `CALENDAR_REQUEST_SCRIPT` (asks if not determined, then reads; only `POST /api/calendar/access` and `debug_calendar.py`). EventKit expands repeating events; events cover local midnight to midnight.
- Settings: `calendar_events` (off by default, so nobody gets a prompt they didn't ask for) and `hidden_calendars` (calendar ids unchecked, so new calendars show). Today's list response has `calendar` = None while off (Calendar not read), else `{access, events}`; each event has id, title, calendar, color, label (`event_time_label`: "All day", "9:30 – 10:30 AM", "11:00 AM – 1:00 PM", "6:05 PM", "Until …", "From …") and state ("past", "now" or None). Canceled events and hidden calendars are left out (`visible_events`); order is all-day first, then start time.
- Clicking an event opens `ical://ekevent/<eventIdentifier>?method=show&options=more` (unencoded: validated ids only use characters allowed in a URL path). Not yet confirmed on a real Mac that Calendar shows the event rather than just opening.
- A lasting read problem is logged once (`CalendarLog`), cleared when a read works.

## Things URL scheme gotchas
- `tags=` replaces all tags, so always send the full list. Tags are comma-separated, and a tag containing a comma cannot be written, so it is refused.
- Tags that don't exist in Things are silently ignored. That's why the P1–P5 tags must exist (the UI warns) and why every write is confirmed by re-reading the database.
- A wrong auth token also fails silently. The only symptom is that the change never appears, which is reported as `write_failed`.
- Unknown tags are dropped silently, so while any of P1–P5 is missing Do Things sends no writes (refresh skipped, moves to a missing priority refused with instructions). Otherwise a missing tag shows up as an unconfirmed write, which looks like a token problem.
- The inline editor (`GET /api/task`, `POST /api/edit`) sends one update built by `plan_edit`: only changed fields; a priority change uses the move rules, and an explicit deadline or When wins. Allowed values are checked against Things' data (`read_edit_options`). `title`, `notes`, `when` (date, `anytime`, `someday`), `list-id` (project or area) and `heading-id` are sent. Things' URL command can't remove a to-do from a project/area/heading, delete it, or edit checklists safely (replacing resets ticks), so the editor doesn't offer those through it. Delete is offered through AppleScript instead (below).
- Things' URL docs say `when`, `deadline` and `completed` "cannot be updated on repeating to-dos". That means the repeating template (never shown, since `rt1_recurrenceRule` rows are excluded): on 2026-11-07 a real copy in Today accepted `when=<date>`. v0.1.7 wrongly locked copies; v0.1.8 removed that.
- `completed=true` / `completed=false` completes or reopens a to-do. `Change.tags` is None for these, so no `tags=` is sent and the tags are left alone.
- `deadline=` with an empty value clears the deadline. `when=YYYY-MM-DD` sets the start date.
- Commas between tags are sent unencoded and spaces as `%20`, matching Things' documented format.

## Move to Trash (v1.5.0, AppleScript)
- The URL scheme has no delete, so "Move to Trash" (editor of an open task, after an in-card confirmation) uses `osascript`: `tell application "Things3" to delete to do id (item 1 of argv)`. Things moves the to-do to its Trash (`trashed = 1`), it doesn't erase it; confirmed on a real task 2026-11-08 ("Test 2").
- The task id is validated (`is_valid_task_id`) and passed as an argument, never written into the script (`build_trash_command`). `move_to_trash` shares `_send_and_confirm` with the URL writes (its send step is `run_trash_script`) and waits for `trashed = 1`; a vanished row doesn't count.
- No auth token is involved. It needs macOS's Automation permission for the app that runs the server (Terminal, or Shortcuts when started from the shortcut). Denied, osascript fails with "Not authorized to send Apple events to Things3. (-1743)", which is logged (the command holds no secret). The page lists the Automation checks (`TRASH_FAILED_STEPS`) instead of the token checks.
- Completed tasks open read-only and can't be trashed (409). Refresh rules never trash. A trashed task in progress of a sequential project no longer matches its record, so the next refresh starts the next task, as after completing it.

- Time zone (v1.0.0): "today" and local midnight come from the Mac's own time zone (`today_local` uses `date.today()`; `start_of_day` uses a naive datetime's `timestamp()`, which applies the system zone and daylight saving). There is no hard-coded zone; don't reintroduce one, since anyone can download Do Things. Tests set `TZ` and call `time.tzset()` to check this.
- A browser that disconnects mid-request raises `ConnectionError` while the reply is sent. `Handler.handle` ignores it, and `_run` sends the reply outside its `try` so it isn't logged as a Things read error.
- The page updates optimistically: drags, reorders, check-offs and edit saves change the DOM first, then `enqueue` sends the request. Requests run one at a time in order (`saveQueue`); rows are dimmed (`.saving`) and not draggable until confirmed, opening the editor waits for pending changes, and the list isn't refreshed until the queue is empty. Then `load()` redraws from Things, which undoes anything Things didn't apply. `load()` checks again after its request returns and doesn't draw over an editor, drag or change started meanwhile (a refresh can take seconds when it writes).
- Do Things' Today ignores `deadlineSuppressionDate` (v0.1.29): Things keeps a due task out of its own Today once the user removes it, but Do Things always lists what is due, and refresh rule 4 then gives an undated one a start date of today (which puts it back in Things' Today; chosen by the user).
- Sequential marker (v0.1.28): `sequence_labels` gives each task a sequential project started (a `sequence_pulls.json` record that `find_pulled` still matches) the label "task N of M" (`sequence_place`): N = completed to-dos in the project (`count_completed`, headings included) + the task's position among the open ones in project order (v0.1.29; v0.1.28 used + 1), M = completed + open. `task_to_json` sends it as `sequence`; the page shows it after the project name. The edit preview keeps it only if the edit leaves the start date and project unchanged.
- Refresh pause (v0.1.27): when `apply_refresh_rules` reports an unconfirmed write, `RefreshPause.paused` is set and later refreshes skip the rules; the list response's `refresh_paused` drives the red bar. Cleared by `POST /api/refresh/retry`, a new token, or a server restart. Manual writes are always tried.
- `errors.log` uses a `RotatingFileHandler` (1 MB, one backup).
- `HTTPServer` is single-threaded on purpose, so writes to Things and to the order file never overlap.
- Starting `serve.py` when port 8765 is already in use just opens the page and exits. The Shortcut relies on this.
- Request checks: the Host header must be `127.0.0.1:8765` or `localhost:8765`, and POSTs need `X-Do-Things: 1`.
- Writes stop at the first failure in a refresh, so a bad token costs one 5-second wait per refresh, not one per task.
- `index.html` builds task rows with `textContent`. Keep it that way: task titles are user data.
- Drag-and-drop uses HTML5 drag events. The insert position is found from row midpoints, and the page does not refresh during a drag or a save (`state.drag` and `state.busy`).
